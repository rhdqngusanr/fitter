# 화면 QC

**정적 검사가 통과했다는 말과 "화면을 검사했다"는 말은 다른 말이다.**
`pnpm qc` 는 브라우저를 열지 않고 `pnpm test` 는 웹 테스트가 0개다.
이 스킬이 그 빈 자리를 메운다.

목록의 근거는 `brain/90-규약/화면 QC 목록.md` 에 있다 — **왜 그 항목을 보는지**가
거기 적혀 있고, 전부 실제로 겪은 결함이다. 아래는 그걸 실행하는 절차다.

## 인자

- 없으면 **전체** (아래 대상 표 순서대로)
- 시안 ID 나 경로를 주면 그것만: `/qc-screens P-01`, `/qc-screens /admin`

## 0단계 — 준비

1. **정적 검사를 먼저 돌린다.** `pnpm qc`
   error 가 있으면 **거기서 멈추고 보고한다.** 1층이 깨진 채로 화면을 보면
   원인이 섞인다.
2. 개발 서버를 띄운다. **`preview_start` 를 쓴다 — Bash 로 서버를 돌리지 않는다.**
   ```
   preview_start { name: "api-dev" }    # :3001 (watch)
   preview_start { name: "web-dev" }    # :3000
   ```
3. **웹이 3000번이 아니면 클라이언트 fetch 가 CORS 로 막힌다.** API 의 `WEB_ORIGIN`
   이 `http://localhost:3000` 고정이다. `launch.json` 이 그렇게 잡혀 있다.

> [!warning] 화면이 통째로 비어 있으면 `.next` 를 의심하라
> 빌드를 개발 서버가 켜진 상태로 돌리면 `.next` 가 덮인다. SSR HTML 에는 내용이
> 있는데 브라우저 DOM 은 빈 Suspense 경계뿐이고 **콘솔 에러도 서버 에러도 없다.**
> 서버 재시작만으로는 안 될 때가 있다.
> ```bash
> rm -rf apps/web/.next
> ```
> 그리고 `preview_start` 를 다시 한다. 코드 문제로 오진하기 전에 이걸 먼저 배제하라.

`support.js` 가 템플릿에서 DOM 을 만들어서 소스에는 최종 레이아웃이 없다.
`preview_start { name: "design-static" }` 로 `:4321` 에 뜬다.

## 1단계 — 시안을 먼저 연다

해당 시안을 렌더하고 **상태 칩을 전부 눌러본다.** 시안이 그린 상태 수가 곧
완료 기준이다. 그 목록을 적어두고 시작한다.

## 2단계 — 렌더 검사 (R1~R7)

각 화면에서 아래를 확인한다. **측정은 `javascript_tool` 로 `getComputedStyle` 을
읽는다** — 스크린샷 눈대중이 아니라 숫자로 비교한다.

- **R1 화면이 그려지는가** — `#main` 이 비지 않았는가, 콘솔 에러 0,
  스켈레톤이 영구히 남지 않는가
- **R2 숨어서 못 고르는 컨트롤** — `scrollWidth > clientWidth` 인 컨테이너에
  **선택해야 하는** 항목이 들어 있지 않은가
- **R3 모바일 가로 스크롤** — 390px 에서 `body.scrollWidth <= innerWidth`
- **R4 상태가 갈라지는가** — 빈 상태 / 로딩 / 에러 / 권한 분기.
  **"못 불러온 것"과 "0건"이 구분되는가.** 검증 오류가 실제 400 을 받아 뜨는가
- **R5 조건부 404** — 승인·소유·상태가 걸린 링크를 **눌러본다.**
  조건 미달이면 링크가 아예 없어야 한다
- **R6 되돌릴 수 없는 조작** — 확인 단계가 있는가, 되돌릴 수 있으면 그 경로가
  화면에 있는가, 없으면 그렇다고 적혀 있는가
- **R7 치수** — 2단 `grid-template-columns`·`gap`, 카드 `padding`·`radius`,
  **터치 타깃 44px 미만이 없는가**, 앵커 `scroll-margin-top`

데스크톱과 **390px 둘 다** 본다. 관리자만 1440px 단독이다(모바일 미지원).

## 3단계 — 판단 검사 (J1~J7)

**여기가 이 스킬의 값이다.** 단정문으로는 영원히 안 잡힌다.

- **J1 두 문장이 모순되지 않는가** — 같은 화면의 두 곳이 다른 말을 하는가
- **J2 버튼이 약속한 곳으로 가는가** — 라벨과 실제 이동이 같은가
- **J3 결과 문구가 새 조치로 읽히지 않는가**
- **J4 카피가 지킬 수 있는 말만 하는가** — **화면의 문장을 코드·스키마와 대조한다.**
  약속한 기한이 어디서 강제되는지, 언급한 정렬이 실제 쿼리와 같은지,
  언급한 제약이 실제 인덱스와 같은지 **파일을 열어 확인한다.**
  기억으로 판단하면 그럴듯한 거짓말을 통과시킨다
- **J5 없는 것을 있다고 말하지 않는가** — 세는 곳 없는 숫자, 저장할 곳 없는 입력,
  **없는 안전장치**
- **J6 화면 없는 메뉴** — 링크는 404, 회색은 약속이다. 둘 다 안 된다
- **J7 화면이 서버보다 무른 말을 하는가** — 화면이 "된다"는데 서버가 막는가

## 상태를 만들어야 할 때

빈 상태·에러·권한 분기는 시드 데이터로 안 나오는 게 많다. 그럴 때는
**Prisma 로 상황을 만들고 확인 후 반드시 되돌린다.**

- **데모 계정은 비밀번호가 없다**(`passwordHash: null` — 의도된 뒷문 방지).
  로그인이 필요하면 **API 로 가입시킨다.** 해시를 직접 만들어 넣지 마라
- 관리자: `pnpm --filter @fitter/api db:seed:admin <email> <password>`
- 임시로 데이터를 바꿨으면 **되돌렸는지 확인까지 하고 보고에 적는다**

## 보고 형식

고치기 전에 **먼저 보고한다.** 검사가 고치기 시작하면 무엇이 문제였는지 흐려진다.

```
## <시안 ID> <라우트>

시안 상태 N개 중 M개 확인

### 결함
1. [R4] <무엇이 잘못됐나> — <어떻게 재현했나> — <왜 문제인가>

### 시안과 다르게 만든 것
- <무엇> — <왜>

### 확인한 치수
- <항목>: 시안 <값> / 구현 <값>
```

**결함이 없으면 없다고 쓴다.** 항목을 채우려고 사소한 걸 올리지 않는다.

## 끝난 뒤

1. 결함을 사용자에게 보고하고 **고칠지 확인받는다**
2. 고쳤으면 `pnpm qc` · `lint` · `typecheck` · `test` 를 다시 돌린다
3. **빌드를 돌릴 거면 개발 서버를 먼저 끈다**
4. `brain/30-설계/시안 대조 결과.md` 에 무엇을 고쳤고 무엇을 못 했는지 적는다.
   **시안과 다르게 만들었으면 이유를 반드시 적는다**

## 화면이 여러 개일 때

화면마다 컨텍스트가 크다. 전체를 돌 때는 `frontend-qc` 서브에이전트에게
**화면 하나씩** 맡긴다 — 그 에이전트는 파일 수정 권한이 없어서 보고가 오염되지 않는다.

```
Agent { subagent_type: "frontend-qc", prompt: "P-01 /pro/profile 을 검사하라. …" }
```

한 화면만 볼 때는 직접 하는 게 빠르다.
