## P0-1. 디자인 시스템 정의

```
반셀프 인테리어 매칭 플랫폼 "Fitter"의 디자인 시스템을 만들어줘.

[서비스 성격]
- 하이엔드가 아니라 "합리적이고 깔끔한" 일반 인테리어가 타겟
- 사진이 주인공인 서비스다. UI는 사진을 방해하면 안 된다
- 사용자는 20~40대, 모바일 비중 70% 이상 예상
- 신뢰감이 핵심 가치 (모르는 시공자에게 내 집을 맡기는 서비스니까)

[만들어줄 것]
하나의 self-contained HTML 파일로, 아래를 실제 렌더링해서 보여줘.
1. 컬러 팔레트: primary / secondary / 배경 / 텍스트 3단계 / 성공·경고·위험 / 보더
   - 다크모드 대응 포함. 각 색의 hex와 용도를 함께 표기
   - 사진 위에 얹혀도 죽지 않는 색으로. 채도 높은 원색 피할 것
2. 타이포그래피 스케일: Pretendard 기준, display/h1/h2/h3/body/caption 6단계
   각각 size, weight, line-height 명시
3. 스페이싱 스케일(4px 베이스)과 라운드, 그림자 3단계
4. 컴포넌트 실물: 버튼(primary/secondary/ghost, 3사이즈, disabled/loading),
   인풋, 셀렉트, 태그·칩(공종 필터용), 뱃지(시공자 인증/상태),
   카드(사진 카드, 시공자 카드), 아바타, 토스트, 빈 상태(empty state), 스켈레톤
5. 각 요소마다 CSS 변수명을 함께 표시해줘 (예: --color-primary-500)

[제약]
- 오늘의집 카피 금지. 사진 그리드가 중심인 건 같아도 톤은 달라야 한다.
  오늘의집이 "따뜻한 라이프스타일"이면 Fitter는 "정직하고 명료한 실무 도구" 쪽으로.
- 이미지는 실제 URL 대신 회색 플레이스홀더 div로
- 외부 CSS 프레임워크 없이 순수 CSS 변수 + 최소한의 CSS로
- WCAG AA 대비율을 만족시키고, 각 조합의 대비율 수치를 표기해줘

먼저 "왜 이 색과 톤을 골랐는지" 5줄로 설명한 다음 HTML을 만들어줘.
```

**결과 반영:** 확정된 컬러 토큰과 타이포 스케일을 [[디자인 원칙]]에 기록한다.

## P0-2. 화면 목록 확정

> 먼저 [[화면 목록]] 노트의 현재 잠정 목록을 프롬프트에 함께 붙여넣는다.

```
[아래 두 가지를 붙여넣기]
1. brain/10-제품/서비스 정의.md 전문
2. brain/30-설계/화면 목록.md 전문 (현재 잠정 목록)

위 서비스의 MVP 화면 목록을 확정해줘. 아직 디자인 말고 목록과 구조만.

각 화면마다 아래를 표로 정리:
- 화면 ID (예: C-01)
- 화면명
- 접근 권한 (비로그인 / CUSTOMER / PRO / ADMIN)
- 이 화면의 단 하나의 목적 (한 문장)
- 주요 UI 요소
- 진입 경로와 이탈 경로
- 이 화면에서 발생할 수 있는 실패/빈 상태

[반드시 답할 것]
- 붙여넣은 잠정 목록에서 빠진 화면과 불필요한 화면
- 온보딩에서 역할을 어떻게 고르게 할지. 한 계정이 두 역할을 다 가질 수 있는가?
  (현재 전제는 계정당 한 역할. 근거와 함께 동의하거나 반박해줘)
- 비로그인 사용자가 어디까지 볼 수 있는가.
  포트폴리오 갤러리는 SEO 유입을 위해 열고 싶지만, 의뢰는 저작권 리스크 때문에
  닫는 게 안전하다. 이 트레이드오프를 판단해줘.
- 컨택 요청 → 수락 → 연락처 공개의 상태 변화가 어느 화면에서 일어나는가

화면 수가 25개를 넘으면 MVP가 아니다. 넘으면 뭘 쳐낼지 함께 제안해줘.
결과를 마크다운 표로 출력.
```

**결과 반영:** [[화면 목록]] 노트를 확정 버전으로 갱신하고 status를 `확정`으로 바꾼다. 역할 관련 판단이 나오면 [[열린 질문]] Q2를 갱신한다.

## P0-3. 핵심 화면 시안

> **한 번에 하나씩.** 여러 화면을 한꺼번에 요청하면 품질이 급락한다.

```
앞서 만든 디자인 시스템(CSS 변수)을 그대로 사용해서
"[화면명]" 화면의 고신뢰도 시안을 self-contained HTML로 만들어줘.

[화면 목적]
[P0-2에서 확정한 그 화면의 목적 한 문장]

[요구사항]
- 모바일(390px) 우선, 데스크톱(1280px) 대응까지 반응형으로. 두 폭 모두 확인 가능하게
- 더미 데이터는 실제 서비스처럼 현실적으로 채울 것
  (예: "성북구 · 24평 · 아파트 · 도배+장판 · 8월 중순 희망")
- 인터랙션 상태를 전부 보여줄 것: 기본 / 호버 / 로딩(스켈레톤) / 빈 상태 / 에러
- 실제 동작하는 필터·토글은 순수 JS로 구현 (localStorage 사용 금지)
- 접근성: 시맨틱 태그, aria-label, 키보드 포커스 링

[화면을 만들기 전에 먼저 답해줘]
1. 이 화면에서 사용자가 3초 안에 이해해야 하는 단 하나는 무엇인가
2. 가장 크게, 가장 먼저 보여야 할 요소는 무엇인가
3. 내가 놓친 상태(state)가 있는가
```

**진행 순서**

1. 랜딩 (G-01) — 비로그인, 서비스 이해 + 가입 유도
2. **의뢰 등록 (C-01)** — 가장 중요. 여기서 이탈하면 끝. → [[엔티티 - ReferenceRequest]]
3. 의뢰 목록/상세 (P-04, P-05) — 시공자가 보는 화면
4. 포트폴리오 등록 (P-02) — [[이미지 파이프라인]] UX의 실체
5. 시공자 목록/상세 (C-04, C-05)
6. 컨택 관리 (M-01, M-02) — [[상태머신 - 컨택]] 상태가 화면에 드러나는 곳
7. 역할 선택 온보딩 (G-04)

## P0-4. 시안 자체 검수

```
지금까지 만든 화면 시안들을 한꺼번에 놓고 냉정하게 비평해줘. 칭찬은 필요 없다.

[검수 항목]
1. 일관성: 같은 의미의 요소가 화면마다 다르게 생기지 않았는가
2. 정보 위계: 각 화면에서 제일 중요한 게 제일 크고 먼저인가
3. 이탈 지점: 사용자가 포기할 가능성이 가장 높은 화면과 그 이유 3개
4. 모바일: 한 손 엄지로 닿지 않는 위치에 핵심 버튼이 있지 않은가
5. 빈 상태: 서비스 초기엔 의뢰도 포트폴리오도 0개다. 그때 화면이 처참하지 않은가.
   이게 매칭 플랫폼 최대 난점인 콜드스타트 문제다. 화면 차원의 대응책을 제안해줘.
6. 신뢰: 처음 온 사람이 "이 시공자한테 우리 집을 맡겨도 되나"를 판단할 근거가 화면에 있는가

각 문제마다 [문제] [왜 문제인지] [구체적 수정안] 세 줄로.
가장 치명적인 것부터 순서대로, 최대 10개.
```

**결과 반영:** 빈 상태 대응책을 [[리스크 - 콜드스타트]]에 추가한다.
