# P5 - 배포와 문서화

> 포트폴리오의 승패는 여기서 갈린다. 코드가 아니라 **설명**이 평가받는다.

---

## P5-1. 시드 데이터와 데모 준비

```
데모용 시드 데이터 스크립트를 만들어줘. 포트폴리오 심사자가 로그인해서 볼 화면이다.

[생성할 것]
- WorkCategory 전체 (도배, 장판·마루, 타일, 욕실, 주방, 목공, 필름, 페인트,
  조명·전기, 새시·중문, 철거, 줄눈, 입주청소)
- 행정구역 데이터 (시도 + 시군구 전체)
- 데모 계정: 고객 1, 시공자 3(승인됨 2 / 대기 1), 관리자 1. 비밀번호는 README에 명시
- 현실적인 의뢰 30건, 포트폴리오 60건, 컨택 요청 20건(상태 다양하게)
- 성능 테스트용 대량 시드 스크립트 별도 (의뢰 1만, 포트폴리오 3만)

[이미지]
- 실제 사진 대신 색상+텍스트가 들어간 생성 이미지로 (저작권 문제 없이)
- 오프라인에서도 동작하게 로컬 생성 방식을 우선 검토

[중요]
더미 텍스트를 "테스트1, 테스트2"로 채우지 마. 실제 서비스처럼 읽히게 써줘.
예: "성북구 24평 아파트, 도배+장판, 8월 중순 희망, 거주 중"
데모의 설득력이 포트폴리오 평가에 직결된다. 서비스 초기엔 화면이 비어 있는데,
심사자에게 그 빈 화면을 보여주면 안 된다.

완료 조건: seed 스크립트 한 번으로 데모 상태가 완성되고, 초기화도 가능할 것.
```

## P5-2. 성능과 접근성 점검

```
아래 항목을 점검하고 문제를 고쳐줘. 고치기 전에 측정 결과를 먼저 보여줘.

[성능]
- Lighthouse 점수 (모바일 기준). 목표: Performance 85+, Accessibility 95+
- 목록 페이지 초기 로딩 시 전송 바이트, 이미지 총량
- LCP를 유발하는 요소와 개선안
- 번들 크기 분석. 큰 의존성 상위 5개와 대체 가능성
- DB 슬로우 쿼리 (100ms 초과) 전부 목록화

[접근성]
- 키보드만으로 핵심 플로우(의뢰 등록, 컨택 요청) 완주 가능한가
- 스크린리더로 이미지 업로드 컴포넌트가 이해 가능한가
- 색상 대비 위반 전부

각 문제마다 [측정값] [원인] [수정] [수정 후 측정값] 순으로 리포트해줘.
```

## P5-3. 배포와 CI

```
배포 파이프라인을 구성해줘.

[포함]
- GitHub Actions: PR 시 lint + type check + test, main 머지 시 배포
- 프로덕션/스테이징 환경 분리
- 환경변수 관리 (시크릿은 절대 커밋되지 않게)
- DB 마이그레이션 자동 적용 전략 (실패 시 롤백)
- 헬스체크 엔드포인트
- 에러 트래킹 연동 (Sentry 등, 무료 티어)
- 배포 후 스모크 테스트

[비용]
- 예상 월 비용을 항목별로 계산해서 보여줘. 무료 티어 한계도 함께.
  brain/30-설계/기술 스택 결정.md 에서 잡은 목표가 월 5만원 이하다.

완료 조건: main에 푸시하면 자동 배포되고, 배포된 URL에서 데모 계정 로그인이 되는 것.
```

## P5-4. 포트폴리오 README

```
brain/ 폴더 전체를 읽어줘. 특히
- brain/10-제품/문제 정의.md
- brain/10-제품/경쟁 지형.md
- brain/20-도메인/이미지 파이프라인.md
- brain/20-도메인/상태머신 - 컨택.md
- brain/10-제품/리스크 - 가격 신뢰.md
- brain/50-결정/ 의 모든 ADR

이 프로젝트를 개발 포트폴리오로 제출한다. README.md를 다시 써줘.

[구성]
1. 한 줄 소개 + 데모 URL + 데모 계정
2. 왜 만들었나 — 기존 인테리어 시장의 중개 마진 구조와 우리의 가설.
   읽는 사람이 3줄 만에 이해하게
3. 데모 GIF 또는 스크린샷 (촬영해야 할 화면 목록만 제안해줘)
4. 기술 스택과 선택 이유 — ADR-001을 3~4문장으로 압축
5. 아키텍처 다이어그램 (mermaid)
6. 기술적으로 공들인 지점 3가지. 각각 [문제] [접근] [결과] [배운 것] 구조로.
   후보: 이미지 업로드 파이프라인 / 컨택 상태 머신 / 목록 쿼리 성능 최적화
7. ERD
8. 로컬 실행 방법
9. 트러블슈팅 기록 — 실제로 막혔던 것 3개
10. 앞으로의 계획 — 가격 자동 산출 기능의 설계 방향과,
    그것 때문에 지금 스키마를 어떻게 잡아뒀는지 (확장 규약 이야기)

[톤]
- 과장 금지. "완벽한", "최고의" 같은 표현 쓰지 말 것
- 불릿 나열보다 문장으로 설명. 읽는 사람은 채용 담당자다
- 6번이 이 README의 핵심이다. 여기에 가장 많은 분량을 쓸 것

작성 후, 이 README에서 면접관이 파고들 만한 질문 10개를 뽑아줘.
```

## P5-5. 최종 코드 리뷰

```
brain/30-설계/구조적 원칙.md 와 brain/20-도메인/확장 규약.md 를 읽고,
전체 코드베이스를 시니어 개발자 관점에서 리뷰해줘. 나에게 아부하지 마.

[리뷰 관점]
1. 보안: 인증 우회, 권한 누락, 인젝션, 파일 업로드 취약점, 개인정보 노출
   특히 연락처가 ACCEPTED 이전에 새는 경로가 있는지 전수 확인
2. 정합성: 동시성 문제, 트랜잭션 경계, 상태 불일치 가능성
3. 성능: N+1, 불필요한 렌더링, 인덱스 누락
4. 설계: 도메인 레이어가 실제로 분리되어 있는가, 아니면 이름만 그런가.
   도메인 레이어의 import에 프레임워크 이름이 있으면 위반이다
5. 확장성: 확장 규약 5개 조항이 실제 코드에 지켜졌는가.
   2차 가격 기능을 붙일 때 막히는 곳이 있는가
6. 유지보수성: 6개월 뒤의 내가 이해할 수 있는가

[출력 형식]
각 발견마다: [심각도 Critical/High/Medium/Low] [파일:라인] [문제] [실패 시나리오] [수정 방향]
심각도 순으로 정렬. 최대 20개.

Critical과 High는 바로 고쳐줘. Medium 이하는 brain/70-산출물/백로그.md에 추가.
```
