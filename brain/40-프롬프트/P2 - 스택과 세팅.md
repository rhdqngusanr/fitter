## P2-1. 스택 선정 ADR

```
brain/70-산출물/PRD.md 와 아래 brain 노트를 읽어줘.
- brain/30-설계/기술 스택 결정.md
- brain/30-설계/구조적 원칙.md
- brain/20-도메인/이미지 파이프라인.md
- brain/30-설계/권한 모델.md

기술 스택 선정 ADR을 brain/50-결정/ADR-001 - 기술 스택 선정.md 로 작성해줘.

[내 제약과 우선순위 — 이 순서대로 가중치]
1. 확장성. 이건 포트폴리오지만 실제 사업으로 이어질 수 있다.
   트래픽이 100배 늘어도, 기능이 10배 늘어도 갈아엎지 않아도 되는 구조를 원한다.
2. 나는 혼자 개발한다. 초기 속도도 중요하다.
3. 국내 취업 포트폴리오로서의 설득력
4. 이미지가 서비스의 핵심이다. 업로드/변환/CDN 전달이 매끄러워야 한다
5. 비용. 초기엔 월 5만원 이하로 굴러가야 한다

[비교할 후보 — 최소 3개. 더 나은 게 있으면 추가]
A. Next.js(App Router) + Supabase(Postgres/Auth/Storage) + Vercel
B. Next.js + NestJS + PostgreSQL + S3 + Docker/ECS
C. React + Spring Boot + JPA + PostgreSQL + S3 + AWS

[각 후보마다 평가할 축]
- 초기 구현 속도 / 확장 한계가 어디서 오는가(구체적으로: 어떤 규모, 어떤 기능에서 막히는가)
- 이미지 파이프라인(업로드, 리사이즈, 썸네일, CDN, 서명 URL)을 어떻게 푸는가
- 권한 모델(역할 기반 + 소유자 기반)을 어디서 강제하는가
- 검색/필터가 무거워질 때의 경로 (인덱스 → 전문검색 → 별도 검색엔진)
- 2차 가격 엔진처럼 계산 비중 있는 도메인 로직을 붙이기 좋은가
- 벤더 락인 정도와 탈출 비용
- 월 예상 비용 (초기 / 사용자 1만 명 시점)
- 국내 채용 시장에서의 신호

[반드시 다룰 것]
- brain/30-설계/구조적 원칙.md 의 7개 원칙을 각 스택에서 어떻게 지킬 수 있는지
- 지금 선택이 틀렸을 때 갈아타는 마이그레이션 경로

[형식]
Context / Decision Drivers / Considered Options / Decision Outcome /
Consequences(긍정·부정) / Migration Path

결론은 하나로 명확히 내려주되, 내가 다른 선택을 할 경우 뭐가 달라지는지도 남겨줘.
```

**결과 반영:** 사용자가 결정한 뒤 [[기술 스택 결정]] 노트의 status를 `확정`으로 바꾸고 [[ADR 인덱스]]와 [[열린 질문]] Q1을 갱신한다.

## P2-2. 프로젝트 스캐폴딩

```
ADR-001에서 결정한 스택으로 프로젝트를 초기화해줘.
brain/30-설계/구조적 원칙.md 와 brain/20-도메인/확장 규약.md 를 먼저 읽어줘.

[포함]
1. 프로젝트 생성 + 폴더 구조. 도메인 레이어를 프레임워크에서 분리한 구조로.
   구조를 만들기 전에 트리를 먼저 보여주고 내 승인을 받아줘.
2. TypeScript strict 모드, ESLint, Prettier, 커밋 훅(husky + lint-staged)
3. 환경변수 스키마 검증 (zod 등). .env.example 포함
4. 에러 처리 공통 레이어 (도메인 에러 타입 + HTTP 매핑)
5. 로깅 (구조화 로그, 요청 ID 추적)
6. 테스트 세팅 (단위 + 통합). 예시 테스트 1개씩
7. 확장 규약 5조에 따라 domain/pricing/ 디렉터리에
   EstimatePolicy 인터페이스와 NoopEstimatePolicy를 미리 만들어둘 것
8. README 초안
9. .gitignore, 첫 커밋

[하지 말 것]
- 아직 기능 코드는 짜지 마. 뼈대만.
- 불필요한 라이브러리 추가 금지. 각 의존성마다 왜 필요한지 한 줄로 설명해줘.

완료 조건: dev / lint / test 스크립트가 전부 통과할 것.
```

## P2-3. 개발 규칙 정리

```
지금 프로젝트 구조를 스캔하고, 루트 CLAUDE.md에 아래를 추가해줘.

- 실제 폴더 구조와 각 폴더의 책임
- 새 기능을 추가할 때 파일을 어디에 어떤 순서로 만드는지 (레시피)
- 네이밍 컨벤션 (파일, 함수, DB 컬럼, API 경로)
  ※ brain/20-도메인/도메인 용어집.md 의 명명 규칙을 따를 것
- 이 프로젝트에서 절대 하면 안 되는 것 목록
  (예: 컴포넌트에서 DB 직접 호출, any 사용, 도메인 레이어에서 프레임워크 import)
- 커밋 메시지 컨벤션

간결하게. CLAUDE.md 전체가 200줄을 넘지 않게 유지해줘.
상세 내용은 brain/ 노트로 링크만 걸어라. CLAUDE.md는 색인이지 본문이 아니다.
```
