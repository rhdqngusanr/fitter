## P3-1. 도메인 모델과 ERD

```
아래 brain 노트를 전부 읽어줘. 여기 있는 정의를 임의로 바꾸지 마.
- brain/20-도메인/도메인 용어집.md
- brain/20-도메인/확장 규약.md
- brain/20-도메인/엔티티 - User와 역할.md
- brain/20-도메인/엔티티 - ReferenceRequest.md
- brain/20-도메인/엔티티 - PortfolioItem.md
- brain/20-도메인/엔티티 - ContactRequest.md
- brain/20-도메인/엔티티 - WorkCategory.md
- brain/20-도메인/상태머신 - 컨택.md
그리고 brain/70-산출물/PRD.md, brain/70-산출물/유저 스토리.md.

brain/70-산출물/ERD.md 를 작성하고 마이그레이션 파일을 만들어줘.

[포함]
1. mermaid erDiagram으로 전체 ERD
2. 각 테이블별 컬럼 명세 표 (이름, 타입, null 여부, 기본값, 설명, 인덱스 여부)
3. 관계와 카디널리티, 삭제 정책(cascade / restrict / soft delete)
4. 인덱스 설계 — 어떤 쿼리를 위한 인덱스인지 쿼리 예시와 함께
5. 마이그레이션 파일

[확장 규약을 반드시 지킬 것 — 어기면 2차에서 전부 갈아엎어야 한다]
- area_pyeong은 DECIMAL, area_m2는 파생
- WorkCategory는 코드 테이블. 계층 지원. 시드 데이터 포함:
  도배, 장판·마루, 타일, 욕실, 주방, 목공, 필름, 페인트, 조명·전기,
  새시·중문, 철거, 줄눈, 입주청소
- 지역은 시도코드 + 시군구코드. 시공자는 다중 활동지역(N:M)
- ReferenceRequest에 estimate_snapshot JSONB NULL 컬럼
- ReferenceImage에 source_type(SELF/EXTERNAL), source_url, is_takedown_requested
- ContactRequest 상태: REQUESTED / ACCEPTED / DECLINED / EXPIRED / CANCELLED
  전이 제약을 DB와 도메인 레이어 중 어디서 강제할지 명시하고 근거를 남겨줘
- 모든 테이블에 created_at, updated_at. 삭제는 soft delete 기본

[설계 후 자문자답]
1. 2차에서 "공종별 표준 단가표 × 평수 × 자재등급 = 예상 견적 범위"를 붙일 때
   지금 스키마로 가능한가? 불가능하면 지금 뭘 고쳐야 하는가?
2. 시공자 1만 명, 포트폴리오 10만 건일 때 목록 쿼리가 느려지는 지점은 어디인가?
3. 정규화를 깨야 할 곳(비정규화 캐시 컬럼)이 있는가?

완료 조건: 마이그레이션이 실제로 실행되고 롤백까지 되는 것.
```

## P3-2. API 명세

```
brain/70-산출물/ERD.md, brain/70-산출물/유저 스토리.md, brain/30-설계/권한 모델.md 를 읽고
brain/70-산출물/API 명세.md를 작성해줘.

[형식] 엔드포인트마다:
- 메서드, 경로, 목적
- 인증 필요 여부, 필요 역할
- 요청 스키마 (타입 포함)
- 응답 스키마 (성공 / 각 실패 케이스별 상태코드와 에러 코드)
- 권한 규칙 (역할 기반 + 소유자 기반을 분리해서 명시)
- 예시 요청·응답 JSON

[규칙]
- 모든 목록 API는 커서 페이지네이션. 커서 인코딩 방식도 명시
- 필터 파라미터: 공종(복수), 지역(복수), 평수 범위, 주거형태, 정렬
- 에러 응답 포맷 통일: { code, message, details }
- 이미지 업로드는 서명 URL 방식(서버 경유 금지). 흐름을 시퀀스로 그려줘
- Rate limit이 필요한 엔드포인트를 지목하고 이유를 설명

[그룹]
/auth, /me, /reference-requests, /portfolios, /pros, /contacts, /scraps, /reports, /admin

[작성 후 반드시]
- 이 API 설계에서 N+1이 발생할 가능성이 높은 지점 3곳과 대응책
- 권한 검사를 빠뜨리기 쉬운 엔드포인트 3곳
- 상대의 연락처(phone)가 실릴 수 있는 모든 응답을 나열하고,
  각각에서 ACCEPTED 이전에 어떻게 차단되는지 설명해줘
```

## P3-3. 권한과 인증 ADR

```
brain/30-설계/권한 모델.md 와 brain/20-도메인/엔티티 - User와 역할.md 를 읽고
brain/50-결정/ADR-002 - 인증과 권한 모델.md 를 작성해줘.

[결정할 것]
1. 인증 방식 (세션 vs JWT, 리프레시 전략, 소셜 로그인 제공자)
2. 역할 모델. 계정당 단일 역할인가, 역할 전환을 허용하는가.
   현재 전제는 단일 역할이다. 이 판단이 나중에 사업을 제약하는지 검토해줘.
   (시공자가 자기 집을 의뢰하고 싶은 경우가 실제로 있다)
3. 권한 강제 지점: 미들웨어 / 서비스 레이어 / DB(RLS) 중 어디서, 왜
4. 소유자 기반 권한을 어떻게 일관되게 강제할 것인가
5. 시공자 승인 플로우 (미승인 시공자가 할 수 있는 것과 없는 것)
6. 연락처 공개 시점 통제 — 응답 직렬화 단계에서 걸러내는 방식을 검토

각 결정마다 대안과 트레이드오프를 쓰고, 보안 사고 시나리오를 하나씩 상정해서
그 결정이 그 시나리오를 막는지 검증해줘.
```

**결과 반영:** [[권한 모델]] 노트를 확정 내용으로 갱신하고, 역할 관련 결론을 [[열린 질문]] Q2에 반영한다.
