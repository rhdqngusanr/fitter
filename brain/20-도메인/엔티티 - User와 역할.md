# 엔티티 - User와 역할

## User

계정 그 자체. 인증 정보와 역할을 갖는다.

주요 필드는 `id`, `email`, `password_hash`(소셜 전용이면 null), `provider`(LOCAL/KAKAO), `role`(CUSTOMER/PRO/ADMIN), `nickname`, `phone`, `is_active`, `created_at`, `updated_at`, `deleted_at`.

`phone`은 **[[상태머신 - 컨택|컨택이 수락되기 전까지 어떤 API 응답에도 포함되지 않는다.**]] 이건 응답 직렬화 레이어에서 강제한다. → [[권한 모델]]

## 역할은 계정당 하나

잠정 결정이다. 근거는 온보딩 단순화와 권한 모델 단순화.

반론도 있다. 시공자가 자기 집 인테리어를 의뢰하고 싶을 수 있고, 고객이 나중에 시공자로 전환하고 싶을 수도 있다. 이 판단이 나중에 사업을 제약하는지는 [[열린 질문]] Q2에서 다루고, [[P3 - 데이터와 API 설계]]의 P3-3에서 재검토한다.

지금은 단일 역할로 가되, **역할을 User 테이블의 컬럼이 아니라 별도 테이블로 뺄지**는 ERD 설계 때 판단한다. 별도 테이블이면 나중에 다중 역할로 확장하기 쉽다.

## CustomerProfile

고객의 부가 정보. 관심 지역, 관심 공종 정도. 가입 시 필수 입력을 최소화한다. [[타겟 - 고객]]은 폼이 길면 이탈한다.

## ProProfile

시공자의 부가 정보이자 공개 프로필의 실체.

상호 또는 활동명, 소개글, 경력 연차, 보유 공종(N:M → [[엔티티 - WorkCategory]]), 활동 가능 지역(N:M, 시도+시군구), 사업자등록번호(선택), 인증 서류, `is_approved`, `approved_at`, `profile_completeness`.

## 시공자 승인

가입 직후 `is_approved = false`. 관리자가 수동으로 승인한다.

미승인 상태에서 **가능한 것**은 로그인, 프로필 작성, 포트폴리오 작성과 저장, 의뢰 목록 열람이다. **불가능한 것**은 포트폴리오 공개, 컨택 요청 발송, 시공자 목록 노출이다.

작성을 미리 허용하는 이유는 승인 대기 중 빈 화면을 보여주면 돌아오지 않기 때문이다. → [[타겟 - 시공자]]

## 프로필 완성도

채울수록 노출 가산점을 준다는 걸 눈에 보이게 표시한다. 게이미피케이션이자 데이터 수집 유인이다.
