# ADR-002 - 인증과 권한 모델

- **상태:** 채택됨 (Accepted) · 2026-07-25
- **요약 노트:** [[권한 모델]] · **목록:** [[ADR 인덱스]]
- **선행:** [[ADR-001 - 기술 스택 선정]] · [[ERD]]

---

## Context

이 서비스는 모르는 개인에게 자기 집을 맡기는 거래를 중개한다. 그래서 권한 실수의 대가가 크다. 특히 하나는 치명적이다 — **상대의 전화번호가 컨택 수락 전에 새는 것.** 고객의 연락처가 새면 스팸이 가고, 시공자 입장에서는 플랫폼을 거칠 이유가 사라진다.

권한은 두 층이고 성격이 다르다. **역할 기반**(CUSTOMER/PRO/ADMIN, 그리고 승인된 PRO인가)은 요청만 보고 판단할 수 있다. **소유자 기반**(내 의뢰인가, 내 컨택인가)은 리소스를 읽어봐야 안다. 이 둘을 같은 곳에서 처리하면 어디가 진짜 방어선인지 알 수 없게 되고, 그게 보안 사고의 표준 경로다.

이 ADR은 여섯 가지를 정한다. 각 결정마다 **보안 사고 시나리오를 하나씩 상정하고 그 결정이 실제로 막는지** 검증한다. 막지 못하면 결정이 틀린 것이다.

---

## Decision Drivers

1. **연락처가 새지 않는다.** 다른 모든 것보다 우선한다.
2. **빠뜨리기 어려워야 한다.** 개발자가 매번 기억해서 지키는 방식은 반드시 샌다. 기본값이 안전한 쪽이어야 한다.
3. **1인 개발이 감당할 복잡도.** 완벽한 보안보다 실제로 구현되고 테스트되는 보안이 낫다.
4. **테스트로 증명 가능해야 한다.** [[PRD]] 8장의 성공 지표 두 번째가 이것이다.

## 결정 1 — JWT (액세스 짧게 + refresh 로테이션)

**채택.** 액세스 토큰 15분, 리프레시 토큰 30일. 리프레시는 **회전**시키고 재사용을 탐지한다.

**대안과 트레이드오프**

*세션 + 쿠키*는 서버가 즉시 무효화할 수 있어 탈취 대응이 낫다. 그러나 API와 웹이 분리된 구조에서 세션 스토어(Redis)가 인증 경로의 필수 의존이 되고, [[ADR-001 - 기술 스택 선정]]의 무상태 확장 이점을 깎는다.

*JWT*는 검증이 무상태라 확장이 쉽지만 **즉시 무효화가 안 된다.** 그래서 액세스를 짧게 잡아 노출 창을 줄이고, 무효화가 필요한 건 리프레시 쪽에서 처리한다.

**저장 위치가 실제로는 더 중요한 결정이다.** 리프레시 토큰은 `httpOnly; Secure; SameSite=Lax` 쿠키에 둔다. localStorage에 두면 XSS 한 번에 30일짜리 자격이 통째로 넘어간다. 액세스 토큰은 메모리에만 둔다(새로고침하면 리프레시로 다시 받는다).

**소셜 로그인은 카카오 하나.** 다만 [[백로그]] B-01에서 구현을 미뤘다. `users.provider` 컬럼과 분기는 지금 만들어두고 실제 연동만 나중에 붙인다.

**사고 시나리오 — XSS로 토큰이 유출된다.**
공격자가 어떤 경로로든 스크립트를 실행시킨다. 액세스 토큰이 메모리에 있으므로 페이지가 살아 있는 동안은 훔칠 수 있다. 그러나 **15분 뒤 만료되고, 리프레시 토큰은 `httpOnly`라 스크립트가 읽을 수 없다.** 공격자는 장기 지속 접근을 얻지 못한다.
훔친 리프레시 토큰을 쓰는 경우(쿠키 탈취)에는 **회전 + 재사용 탐지**가 작동한다. 같은 리프레시 토큰이 두 번 제시되면 그 계정의 토큰 계열 전체를 폐기한다. 정상 사용자도 로그아웃되지만, 그게 맞다.
**→ 막는다(완화). 완전 차단은 아니고 피해 창을 15분으로 줄이는 방어다.**

## 결정 2 — 계정당 역할 1개, 단 스키마는 열어둔다

**채택.** `users` 컬럼이 아니라 `user_profiles` 테이블. MVP에서는 애플리케이션이 프로필 1개만 만들도록 막는다. → [[ERD]]

**대안과 트레이드오프**

*`users.role` 단일 컬럼*이 가장 단순하다. 그러나 2차에 다중 역할을 열려면 **마이그레이션과 모든 권한 코드의 수정**이 필요하다.

*처음부터 다중 역할 허용*은 유연하지만 MVP에서 감당할 복잡도가 아니다. 모든 목록·상세에서 "지금 어느 모자를 쓰고 있나"를 판단해야 하고, **컨택 한 건에 같은 계정이 양쪽 당사자로 들어올 수 있다.** 그리고 PRO는 승인 심사 대상인데 심사 단위가 계정이 아니면 승인·정지가 지저분해진다.

**이 판단이 사업을 제약하는가.** 제약한다. "시공자가 자기 집 인테리어를 의뢰하고 싶은" 경우는 실제로 있고, 지금은 그 사람이 계정을 하나 더 만들어야 한다. 다만 초기 트래픽에서 그 비율은 무시할 수 있고, **스키마를 열어뒀으므로 여는 시점에 마이그레이션이 필요 없다.** 지금 필요한 탈출구는 설정의 역할 전환 요청(관리자 수동 처리) 하나면 충분하다.

역할 미선택 상태는 `user_profiles` 행이 **없는** 것으로 표현한다. nullable 컬럼보다 정직하다.

**사고 시나리오 — 역할 전환으로 권한을 훔친다.**
사용자가 CUSTOMER로 가입해 의뢰를 올린 뒤 PRO로 전환을 요청한다. 전환이 자동이면 그 순간 자기 의뢰에 자기가 제안할 수 있고, `contact_requests`의 양쪽 당사자가 같은 사람이 된다.
막는 장치가 셋이다. 전환이 **관리자 수동 처리**라 자동으로 일어나지 않는다. `CHECK (requester_user_id <> receiver_user_id)`가 DB에서 자기 자신에게 보내는 컨택을 거부한다. 그리고 PRO 전환은 **승인 심사를 다시 거친다.**
**→ 막는다.**

## 결정 3 — 역할은 Guard, 소유자는 서비스 레이어. RLS는 쓰지 않는다

**채택.** 강제 지점을 층별로 하나씩만 둔다.

| 검사 | 위치 | 이유 |
|---|---|---|
| 인증 여부 | Guard | 요청만 보면 안다 |
| 역할·승인 여부 | Guard (`@Roles`, `@ApprovedPro`) | 요청만 보면 안다 |
| 소유자·당사자 | 서비스 레이어의 재사용 유틸 | **리소스를 읽어봐야 안다** |
| 상태 전이 주체 | 도메인 전이 함수 | 상태와 주체를 함께 봐야 한다 |
| 연락처 노출 | 응답 직렬화 인터셉터 | 결정 6 |

**대안과 트레이드오프**

*DB의 RLS(Row Level Security)*는 강력하다. 애플리케이션이 실수해도 DB가 막는다. [[ADR-001 - 기술 스택 선정]]에서 Supabase를 택했다면 자연스러운 선택이었을 것이다.

쓰지 않는 이유는 셋이다. 첫째, RLS는 **세션 변수로 현재 사용자를 넘겨야** 하는데 커넥션 풀 위에서 이걸 안정적으로 하려면 트랜잭션마다 `SET LOCAL`이 필요하고 Prisma에서는 매끄럽지 않다. 둘째, 정책이 SQL로 흩어져 **테스트하기 어렵고** 도메인 규칙이 두 곳(도메인 코드와 DB 정책)에 살게 된다. 셋째, [[구조적 원칙]] 7조가 "한 곳에서만 강제한다"인데 RLS를 더하면 방어선이 둘이 되어 어느 쪽이 진짜인지 모호해진다.

**대신 DB는 정합성만 책임진다.** FK, CHECK, 부분 유니크 인덱스가 그것이고 이건 사용자가 누구인지와 무관한 규칙이다. → [[ERD]]

**사고 시나리오 — 새 엔드포인트에 가드를 안 붙인다.**
6개월 뒤 `GET /reference-requests/:id/summary`를 급하게 추가하면서 `@Roles`를 빠뜨린다. 인증만 확인하고 데이터를 반환한다.
Guard 방식의 약점이 정확히 여기다. **기본값이 "열림"**이면 빠뜨리는 순간 새어나간다. 그래서 **전역 가드를 인증 필수로 걸고, 공개 엔드포인트만 `@Public()`으로 명시적으로 뚫는다.** 기본값을 "닫힘"으로 뒤집는 것이다. 역할 검사를 빠뜨려도 최소한 비로그인에게는 안 나간다.
소유자 검사 누락은 이걸로 못 막는다. 그건 결정 4에서 다룬다.
**→ 부분적으로 막는다. 전역 기본값 반전이 핵심이고, 나머지는 리뷰와 테스트로 보완한다.**

## 결정 4 — 소유자 검사는 재사용 유틸 하나로 강제한다

**채택.** 엔드포인트마다 조건문을 짜지 않는다.

```ts
assertOwner(resource.ownerId, actor.id);      // 소유자만
assertParticipant(contact, actor.id);         // 컨택 당사자만
```

**대안과 트레이드오프**

*엔드포인트마다 직접 검사*는 유연하지만 **반드시 어딘가 빠진다.** 그리고 빠진 걸 발견하는 방법이 없다.

*데코레이터로 선언적 처리*(`@Owns('referenceRequest')`)는 더 깔끔해 보이지만, 리소스를 어떻게 로드할지가 엔드포인트마다 달라서 결국 각 케이스를 데코레이터 인자로 밀어넣게 된다. 복잡도가 옮겨갈 뿐이다.

그래서 **유틸 함수 + 규칙**으로 간다. 규칙은 CLAUDE.md 금지 목록에 있고, [[자동 QC]]에 "리소스를 조회한 뒤 `assertOwner`/`assertParticipant` 없이 수정하는 서비스 메서드" 검사를 추가한다.

**소유자 실패는 404로 응답한다.** 403은 "그 리소스가 존재한다"를 알려준다. 남의 `DRAFT` 의뢰나 남의 컨택은 존재 자체가 비밀이다. → [[API 명세]]

**사고 시나리오 — IDOR. 남의 의뢰 ID로 수정한다.**
공격자가 자기 의뢰 ID의 패턴을 보고 다른 UUID를 넣어 `PATCH /reference-requests/:id`를 호출한다.
UUID라 추측은 어렵지만 컨택 화면에서 상대 의뢰 ID를 정당하게 알게 되는 경로가 있다. 서비스가 리소스를 로드한 뒤 `assertOwner`를 부르므로 **`customerUserId !== actor.id`에서 404**가 난다.
가장 위험한 건 이 검사가 **곁가지 엔드포인트에서 빠지는 것**이다. `POST /reference-requests/:id/images`가 대표적이다 — 남의 의뢰에 사진을 붙일 수 있으면 저작권 신고가 엉뚱한 계정으로 간다. 그래서 [[API 명세]]에 "권한을 빠뜨리기 쉬운 엔드포인트 셋"을 미리 지목해뒀다.
**→ 막는다. 단 규율이 아니라 유틸 + QC 검사로 받쳐야 한다.**

## 결정 5 — 승인은 별도 게이트. 미승인 PRO도 작성은 할 수 있다

**채택.** `role = PRO`인 것과 **승인된 PRO**인 것은 다르다. `@ApprovedPro()` 가드를 따로 둔다.

| 미승인 PRO | 가능 | 불가능 |
|---|---|---|
| 로그인 | ○ | |
| 프로필 작성 | ○ | |
| 포트폴리오 작성·저장 | ○ | **공개** |
| 의뢰 목록 열람 | ○ | |
| 컨택 요청 발송 | | ✕ |
| 시공자 목록 노출 | | ✕ |

**작성을 미리 허용하는 이유는 제품 판단이다.** 승인 대기 중 할 일이 없으면 [[타겟 - 시공자]]는 돌아오지 않는다. 대기 시간을 빈 화면으로 두면 그 사람을 잃는다.

**공개 조건이 두 개**라는 게 핵심이다. 포트폴리오가 `PUBLISHED`이고 **소속 시공자가 승인됨**이어야 한다. 하나만 보고 공개하는 실수가 나기 쉬워서 [[ERD]]의 인덱스와 [[유저 스토리]] US-024 테스트가 이걸 겨냥한다.

승인 철회 시 공개는 즉시 중단되지만 **이미 공개된 연락처는 회수하지 않는다.** 회수할 방법이 없기 때문이고, 없는 능력을 있는 척하지 않는다.

**사고 시나리오 — 미승인 시공자가 API를 직접 호출한다.**
화면에서 버튼이 비활성이어도 공격자는 `POST /contacts`를 그대로 부른다.
UI 차단은 방어가 아니다. `@ApprovedPro()` 가드가 서버에서 403을 반환한다. 그리고 목록 노출은 가드가 아니라 **쿼리 조건**(`pro.is_approved = true`)이라 우회 경로 자체가 없다.
**→ 막는다.**

## 결정 6 — 연락처는 응답 직렬화 한 곳에서, 기본값 "제외"로 막는다

**채택.** 이 ADR에서 가장 중요한 결정이다.

**대안과 트레이드오프**

*컨트롤러마다 조건문*은 절대 안 된다. 연락처가 실릴 수 있는 경로가 [[API 명세]] 기준 아홉 곳이고, 하나만 빠져도 사고다. 그리고 새 엔드포인트가 생길 때마다 개발자가 기억해야 한다.

*DTO에서 아예 뺀다*는 방법도 있다. 안전하지만 수락 후에 보여줘야 하므로 결국 어딘가에서 조건부로 넣어야 한다.

그래서 **응답 직렬화 인터셉터**에서 처리한다. 규칙은 두 줄이다.

1. **기본값은 "포함하지 않음".** 명시적으로 공개 조건을 만족할 때만 채운다. 새 엔드포인트를 추가해도 별도 조치 없이 안전한 쪽이 기본이다.
2. **마스킹이 아니라 키 자체를 없앤다.** `"phone": "010-****-****"`는 값이 있다는 걸 알려주고, 언젠가 마스킹 로직이 빠지면 그대로 새어나간다. 키가 없으면 그럴 일이 없다.

공개 조건은 하나뿐이다. **컨택이 `ACCEPTED`이고 조회자가 그 컨택의 당사자일 때.** 본인의 `GET /me`는 예외다.

**로그도 같이 막는다.** 응답에서 막아놓고 로그로 새면 막은 게 아니다. pino `redact`에 `*.phone`, `req.body.phone`, `authorization`, `cookie`를 걸어뒀다. → `apps/api/src/common/logging/logging.module.ts`

**목록 쿼리는 애초에 `phone`을 SELECT하지 않는다.** 직렬화에서 걸러지더라도 메모리에 올리지 않는 게 낫다. 스택 트레이스나 디버깅 출력에 섞일 여지를 없앤다.

**사고 시나리오 — 컨택 목록 API가 상대 정보를 통째로 반환한다.**
개발자가 `GET /contacts`에서 `include: { receiver: true }`를 쓴다. Prisma가 `users` 행 전체를 가져오고 컨트롤러가 그대로 반환한다. 화면은 이름만 쓰므로 **아무도 눈치채지 못한다.** 그러나 응답 JSON에는 전화번호가 들어 있다.
이게 이 프로젝트에서 가장 현실적인 사고다. 직렬화 인터셉터가 `ACCEPTED`가 아닌 항목의 `phone`을 제거하므로 막힌다. 그리고 **테스트가 이걸 검증한다** — "REQUESTED 상태의 컨택 목록 응답 JSON에 `phone` 키가 존재하지 않는다"([[유저 스토리]] US-042).
**→ 막는다. 그리고 이 시나리오가 테스트로 고정되어 있다는 게 핵심이다.**

---

## Consequences

**긍정**
- 연락처 노출 통제가 한 곳에 모여 있고 기본값이 안전하다. 새 엔드포인트가 자동으로 보호된다.
- 권한 층이 분리되어 있어 "어디가 방어선인가"에 답할 수 있다.
- 무상태 인증이라 API 인스턴스를 늘리는 데 제약이 없다.
- 모든 결정이 테스트 가능한 형태다. 특히 결정 6은 테스트가 곧 명세다.

**부정 / 감수하는 것**
- JWT라 **즉시 무효화가 안 된다.** 액세스 15분이 그 대가이고, 계정 정지 시 최대 15분의 창이 남는다.
- RLS를 안 쓰므로 **애플리케이션이 실수하면 DB는 막아주지 않는다.** 이건 결정 3·4·6의 장치들이 감당한다.
- 계정당 1역할이라 시공자가 자기 집을 의뢰하려면 계정이 하나 더 필요하다.
- 직렬화 인터셉터가 모든 응답을 거치므로 아주 큰 응답에서는 비용이 있다. 목록이 커서 페이지네이션이라 상한이 있어 현재 규모에서는 문제가 아니다.

## Migration Path

**JWT → 세션.** 즉시 무효화가 꼭 필요해지면(예: 계정 도용 신고가 늘면) 리프레시 토큰을 DB에 저장하는 방식으로 먼저 옮긴다. 액세스 토큰 검증은 그대로 두고 리프레시만 서버 상태로 만드는 중간 단계가 있다. 전면 세션 전환은 그다음이다.

**단일 역할 → 다중 역할.** 스키마는 이미 `user_profiles`라 **마이그레이션이 필요 없다.** 애플리케이션의 "프로필 1개" 제한을 풀고, 요청마다 활성 역할을 지정하는 방법(헤더 또는 경로 접두사)을 정하면 된다. 컨택의 양쪽 당사자가 같은 사람이 되는 경우는 이미 DB CHECK가 막고 있다.

**애플리케이션 강제 → RLS 추가.** 하려면 RLS를 **추가 방어선**이 아니라 대체로 가야 한다. 두 곳에서 강제하면 어느 쪽이 진짜인지 모호해진다. 옮긴다면 소유자 검사부터 옮기고, 그때 서비스 레이어의 유틸을 제거한다.

**소셜 로그인 추가.** `users.provider`와 분기가 이미 있다. 제공자를 늘리려면 `provider` enum에 값을 추가하고 콜백 핸들러를 붙인다. 같은 이메일의 계정 연결 정책은 그때 정한다(현재는 기존 소셜 로그인으로 안내).
