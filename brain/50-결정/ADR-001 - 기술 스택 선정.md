# ADR-001 - 기술 스택 선정

- **상태:** 채택됨 (Accepted) · 2026-07-25
- **요약 노트:** [[기술 스택 결정]] · **목록:** [[ADR 인덱스]]
- **관련 예정 ADR:** ADR-002 인증·권한, ADR-010 가격 정책(2차)

---

## Context — 배경

Fitter는 "이렇게 해주세요" 사진을 올리는 고객과, 자기 시공 포트폴리오를 올리는 반셀프 인테리어 작업자를 **사진 기준으로 직접 연결하는 양방향 매칭 플랫폼**이다. 제품의 성격상 세 가지가 스택 선택을 지배한다.

1. **사진이 제품의 전부다.** 업로드 경험과 목록 로딩 속도가 곧 품질이다. 서명 URL 직접 업로드, 클라이언트 리사이즈, 파일 타입 위조 방어(매직 넘버), 썸네일 파생, EXIF 제거, 고아 파일 정리가 필수다.
2. **민감한 권한 규칙이 있다.** 상대의 전화번호는 컨택이 수락된 경우에만 노출되어야 하며, 목록·상세·프로필 어느 경로로도 새어나가면 안 된다. 이 통제는 응답 직렬화 한 곳에서 강제되어야 한다.
3. **2차 확장이 예정돼 있다.** 평수 × 공종 × 지역 × 자재등급 데이터를 지금부터 구조화해 쌓고, 2차에 자동 견적(계산 도메인)을 얹는다. 스키마와 도메인 경계가 이를 미리 수용해야 한다.

개발 조건은 **1인 개발, 4~6주 MVP**이며, 트래픽 100배·기능 10배가 되어도 **갈아엎지 않는 구조**를 요구한다.

---

## Decision Drivers — 결정 기준 (가중치 순)

1. **확장성.** 포트폴리오지만 실제 사업으로 이어질 수 있다. 100배 트래픽, 10배 기능에도 재작성이 없어야 한다.
2. **1인 개발 속도.** 초기 속도가 중요하다.
3. **국내 취업 신호.** → **스타트업·스케일업(제품 엔지니어링) 방향으로 확정.**
4. **이미지 파이프라인 품질.** 업로드·변환·CDN 전달이 매끄러워야 한다.
5. **비용.** 초기 월 5만원 이하.

> **지배적 전제:** *"무한 확장은 스택이 주는 게 아니라 경계 설계가 준다."* 아래 7개 구조 원칙(문서 하단 참조)을 어떤 스택에서도 지킨다는 것을 전제로, 확장성은 세 후보 사이에서 **사실상 동점**으로 본다. 따라서 결정은 ②~⑤ 기준과 **"이 설계를 가장 자연스럽게 담는가"**로 갈린다.

---

## Considered Options — 검토한 대안

| 기준 | A. Next + **Supabase** | B. Next + **NestJS** + PG + S3 | C. React + **Spring** + JPA |
|---|:---:|:---:|:---:|
| ① 확장성 | ○ 서버리스라 워커/장기작업 애매 | ◎ PG + 워커 + 어댑터 | ◎ JVM 대규모 정석 |
| ② 1인 속도 | ◎ 가장 빠름 | ○ 중간 (풀 TypeScript 단일 언어) | △ 최다 구현(2개 언어) |
| ③ 취업 신호 | ○ 스타트업 결 | ◎ 모던 스타트업/스케일업 | ◎ 대기업·금융·SI 정석 |
| ④ 이미지(핵심) | ○ 내장이라 **보여줄 깊이가 가려짐** | ◎ 실제 파이프라인을 그대로 노출 | ◎ 가능하나 무겁다 |
| ⑤ 비용 <5만 | ◎ 단순 | ◎ R2(egress 무료)로 저렴 | ○ AWS 운영비 상승 |
| 7원칙·하이라이트 적합 | △ RLS가 "도메인 분리" 철학과 충돌 | **◎ 1:1로 매핑** | ◎ 되지만 무겁다 |

**A. Next.js(App Router) + Supabase(Postgres/Auth/Storage) + Vercel**
가장 빠르게 출시할 수 있고 인증·DB·스토리지가 한 몸이다. 그러나 Supabase의 최대 강점인 RLS·클라이언트 직접 접근·번들 인증은 이 프로젝트가 지향하는 **애플리케이션 레이어 클린 아키텍처(도메인 분리 · 단일 강제점 · 이벤트 · 어댑터)**를 흡수·은닉한다. 강점을 살리면 포트폴리오 서사가 약해지고, 살리지 않으면 A의 속도 이점이 사라진다. 또한 썸네일 파생·고아 파일 정리·도메인 이벤트 같은 **백그라운드 작업이 서버리스 모델에 어색하게 얹힌다.**

**B. Next.js + NestJS + PostgreSQL + S3호환 스토리지 + Docker**
프론트/백엔드 분리형. NestJS가 이 프로젝트의 구조 원칙에 거의 1:1로 대응한다(하단 매핑 참조). 풀 TypeScript 단일 언어로 1인 개발에서 C보다 훨씬 빠르며, Postgres + S3호환 + Docker 조합은 **벤더 락인이 가장 낮아 "안 갈아엎는다"는 요구에 가장 정직하게** 답한다. 이미지 파이프라인을 표준 방식(서명 URL + sharp + 매직넘버 + 워커)으로 직접 구현해 **면접에서 파고들 깊이를 그대로 노출**한다.

**C. React + Spring Boot + JPA + PostgreSQL + S3 + AWS**
국내 백엔드 채용의 정석 신호이며 JVM의 대규모 확장 서사가 가장 강하다. 그러나 **2개 언어**라 1인 4~6주 MVP에서 구현량이 가장 크고, 이미지 워커 생태계가 무겁다. 취업 방향이 대기업·금융·SI 백엔드였다면 1순위였겠으나, **스타트업·스케일업 방향으로 확정**되면서 B 대비 이점이 상쇄된다.

---

## Decision Outcome — 결정

**채택: B — Next.js + NestJS + PostgreSQL + S3호환 스토리지.**

구체 구성:

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어 | TypeScript (strict) 전 계층 | 1인 개발 생산성, 프론트/백 지식 공유 |
| 프론트 | Next.js (App Router) + TanStack Query | 포트폴리오 SEO 공개(SSR) / 의뢰 `noindex`, URL 동기화 필터 |
| 백엔드 | NestJS (헥사고날 폴더 구조) | 7원칙 1:1 매핑(하단) |
| DB | PostgreSQL | FK 공종 코드테이블, JSONB 견적 스냅샷, 커서 페이지네이션 |
| ORM | Prisma (저장소 패턴 뒤) | 1인 속도. 어댑터 뒤라 Drizzle/생쿼리로 교체 자유 |
| 스토리지/CDN | Cloudflare R2 (S3 API) + presigned URL | **egress 무료** = 이미지 앱 비용 급소, 락인 없음 |
| 이미지 처리 | sharp(리사이즈·썸네일·EXIF 제거), file-type(매직넘버) | 표준·검증된 실무 도구 |
| 워커/큐 | BullMQ + Redis | 썸네일 파생, 고아 파일 TTL 정리, 이벤트 비동기화 |
| 인증 | Passport(JWT + refresh) + passport-kakao | 이메일 + 카카오. 직접 구현이 곧 신호 |
| 검색 확장 | PG 인덱스/GIN → (필요 시) Meilisearch/OpenSearch | SearchPort 어댑터 뒤에서 무거워질 때만 교체 |
| 초기 호스팅 | 백엔드=Railway/Fly.io, PG=Neon, Redis=Upstash, 프론트=Vercel | 월 5만원 이하로 시작 |

## Consequences — 결과

**긍정**
- 구조 원칙과 두 하이라이트(이미지 파이프라인 · 컨택 상태머신/연락처 통제)를 가장 자연스럽게 구현·전시한다.
- 단일 언어(TS)로 1인 개발 속도를 확보하면서 C의 아키텍처 설득력도 상당 부분 가져온다.
- Postgres + S3호환 + Docker로 벤더 락인이 최소. 어느 클라우드로도 이식 가능.
- 비용 급소(이미지 egress)를 R2로 원천 차단.

**부정 / 감수하는 것**
- Supabase(A) 대비 인증·스토리지 배선을 직접 해야 하므로 초기 셋업이 더 걸린다.
- Redis/워커 등 운영 구성요소가 늘어 인프라 표면적이 A보다 크다. → 초기엔 관리형(Upstash/Neon)으로 운영 부담을 흡수한다.
- 대기업·금융 백엔드 채용의 "Java/Spring 정석 신호"는 C보다 약하다(방향 확정으로 감수).

## 구조 원칙 준수 방법 (7개, NestJS 기준)

이 스택이 아래 원칙들을 **어디서** 강제하는지 명시한다. 원칙 자체는 프레임워크와 무관하게 지킨다.

1. **도메인을 프레임워크에서 분리** → 순수 TS `domain/`. NestJS import는 바깥 링(어댑터/컨트롤러)에만. 도메인 레이어 import 문에 프레임워크 이름 0개.
2. **외부 의존은 어댑터 뒤에** → 스토리지·메일·알림·검색을 Port 인터페이스로 정의, NestJS DI로 구현 주입. MVP 메일은 콘솔 구현.
3. **계산의 자리를 미리 비워둔다** → `domain/pricing/`에 `EstimatePolicy` + `NoopEstimatePolicy`(항상 null). `estimate_snapshot JSONB NULL` 컬럼 예약.
4. **상태 변화는 이벤트를 낳는다** → 컨택 전이가 도메인 이벤트 발행, `@nestjs/event-emitter`로 구독. 인메모리로 시작, 나중에 큐로 교체해도 발행부 불변.
5. **목록은 처음부터 커서 페이지네이션** → 모든 목록 API 커서 기반. 오프셋 금지.
6. **읽기 경로에 원본을 태우지 않는다** → 목록=400px, 상세=1200px 썸네일만. 원본은 보관 전용.
7. **한 곳에서만 강제한다** → 역할 검사=Guard(미들웨어), 소유자 검사=서비스 레이어 재사용 유틸, **연락처 노출=응답 직렬화 Interceptor(기본 미포함, 조건 충족 시에만 채움)**. 흩뿌리지 않는다.

## Migration Path — 되돌리는 길

결정이 틀렸을 때의 탈출 경로. **되돌릴 방법을 적어두는 게 결정의 절반이다.**

- **스토리지 교체(R2 ↔ AWS S3 ↔ GCS):** 전부 S3 호환 API. `StoragePort` 어댑터 구현만 교체.
- **DB 호스팅 이동(Neon → RDS/Cloud SQL/자체호스팅):** 표준 Postgres이므로 덤프·복원으로 이동. 애플리케이션 코드 불변.
- **ORM 교체(Prisma → Drizzle/생쿼리):** 저장소 패턴 뒤에 격리했으므로 도메인·서비스 불변.
- **검색 확장(PG → Meilisearch/OpenSearch):** `SearchPort` 뒤에서 인덱싱 어댑터만 추가. API 계약 불변.
- **프레임워크 전환(B → C, NestJS → Spring):** 취업 방향이 바뀌어 Java/Spring이 필요해지면, **순수 도메인 레이어(로직·모델·테스트)가 이식 명세가 된다.** 바깥 링(컨트롤러·어댑터)만 다시 쓰면 되고 도메인은 그대로 옮긴다. 이것이 원칙 1을 지키는 실질적 이유다.
- **호스팅 확장(관리형 → AWS ECS/GCP Cloud Run):** Docker 이미지 그대로 이동. 컨테이너化가 이 경로를 보장한다.

---

## 다른 선택을 했다면

- **최단기간 출시가 최우선이었다면 → A(Supabase).** 가장 빠르지만 클린 아키텍처 강점이 가려진다.
- **대기업·금융·SI 백엔드가 목표였다면 → C(Spring).** 채용 신호는 최강이나 1인 4~6주엔 구현량이 빠듯하다.
