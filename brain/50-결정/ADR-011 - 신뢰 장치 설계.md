# ADR-011 - 신뢰 장치 설계

- **상태:** 채택됨 (Accepted) · 2026-07-25 · **설계만. 구현은 2차다.**
- **배경 노트:** [[리스크 - 플랫폼 이탈]] · [[리스크 레지스터]] · **목록:** [[ADR 인덱스]]
- **짝:** [[ADR-010 - 가격 정책 모델]] — 가격이 "얼마가 적정한가"라면 이건 "그 사람을 믿어도 되는가"다

> **가정: 법적 판단은 전문가 검토 대상이다.** 아래는 리스크의 모양을 파악해 도입 순서를 정하기 위한 것이고 법률 자문이 아니다.

---

## Context

가격을 안다고 안심되는 게 아니다. [[문제 정의]]의 약한 고리는 이것이었다.

> 중간 마진이 사라지면 **중간이 하던 일도 같이 사라진다.** 종합업체는 마진만 먹는 게 아니라 공정 조율, 품질 책임, 하자 보수, 분쟁 조정을 한다. 그걸 고객이 직접 떠안는다.

[[ADR-010 - 가격 정책 모델]]이 "얼마가 적정한가"를 다뤘다면 이 문서는 나머지를 다룬다. **모르는 개인에게 자기 집을 맡기고, 문제가 생기면 누가 책임지는가.**

그리고 여기에 [[리스크 - 플랫폼 이탈]]이 얽힌다. 연락처를 교환하면 이후 거래는 플랫폼 밖에서 일어난다. 수수료를 받을 지점도, 무슨 일이 있었는지 아는 방법도 없다. **신뢰 장치와 이탈 방지는 같은 문제의 두 얼굴이다** — 거래가 안에 있어야 검증할 수 있고, 검증되어야 신뢰 장치가 작동한다.

---

## 검토한 장치

각 장치마다 **없을 때 실제로 벌어지는 사고**를 먼저 적는다. 사고가 그려지지 않는 장치는 만들 이유가 없다.

### 1. 완료 확인 (Completion Confirmation)

**없으면 벌어지는 일.** 플랫폼은 컨택이 수락됐다는 것만 안다. 실제로 시공이 됐는지, 얼마에 됐는지, 잘 됐는지 전혀 모른다. **그래서 다른 모든 장치가 작동하지 않는다** — 리뷰를 쓸 자격을 판정할 수 없고, 실거래가를 모으지 못하고, 분쟁이 나도 무슨 거래였는지 재구성할 수 없다.

| | |
|---|---|
| 효과 | **매우 높음 (간접).** 다른 장치들의 토대 |
| 구현 난이도 | **낮음.** 알림 + 양방 확인 플래그 |
| 법적 요건 | 없음 |
| 도입 시점 | **1순위** |

컨택이 `ACCEPTED`가 되고 일정 기간이 지나면 양쪽에 묻는다. "시공이 진행됐나요?" 양쪽이 확인하면 **검증된 거래**로 표시한다.

완벽하지 않다. 둘이 짜고 거짓 확인을 할 수 있다. 그러나 **양방 확인 + 컨택 이력 + 시점 기록**이 함께 있으면 단순 조작보다 훨씬 어렵고, 에스크로 없이 얻을 수 있는 최선에 가깝다.

**이 하나가 세 가지를 동시에 준다.** 리뷰 자격의 근거, [[ADR-010 - 가격 정책 모델]] D단계의 실거래가 데이터원, 그리고 [[리스크 - 플랫폼 이탈]]의 이탈률 지표. **가장 싼 장치가 가장 많은 걸 푼다.**

### 2. 리뷰·평점

**없으면 벌어지는 일.** 부실 시공을 한 사람이 아무 흔적 없이 다음 고객을 받는다. 피해가 같은 방식으로 반복되고, 잘하는 시공자는 잘한다는 걸 증명할 방법이 없다. **결국 가격만으로 고르게 되고, 그러면 최저가 경쟁이 품질을 밀어낸다.**

| | |
|---|---|
| 효과 | 높음 |
| 구현 난이도 | 중 |
| 법적 요건 | 명예훼손·허위후기 이슈. 조작 시 제재 사례 있음 |
| 도입 시점 | **2순위** (완료 확인 직후) |

**작성 자격을 완료 확인된 거래로 제한한다.** 이게 없으면 리뷰는 조작에 무방비다. [[MVP 범위]]가 리뷰를 뺀 이유도 정확히 이것이었다 — "거래 검증 없이는 신뢰도가 없다".

사진 필수로 한다. 글만 있는 후기보다 **시공 결과 사진 한 장이 정보량이 훨씬 크고 조작이 어렵다.** 그리고 이 서비스는 어차피 사진이 중심이다.

낮은 평점을 받은 시공자가 반론할 통로가 있어야 한다. 일방적 평판 훼손은 그 자체로 분쟁이 된다.

### 3. 시공자 인증 등급

**없으면 벌어지는 일.** 사업자등록도 배상책임보험도 없는 사람이 시공하다 누수를 낸다. 아랫집 피해가 수백만원인데 **배상 능력이 없다.** 고객은 플랫폼에 항의하고, 플랫폼은 "중개자일 뿐"이라고 답한다. 그 순간 서비스 신뢰가 무너진다.

| | |
|---|---|
| 효과 | 높음 |
| 구현 난이도 | 중 (서류 검수는 사람이 한다) |
| 법적 요건 | 보험 가입 **확인**은 되지만 플랫폼이 **보증**하면 안 된다 |
| 도입 시점 | 3순위 |

현재 MVP에는 관리자 수동 승인(`is_approved`)이 이미 있다. 등급은 그 위에 얹는다.

| 등급 | 조건 |
|---|---|
| 확인됨 | 실명 + 연락처 확인 (현재 승인 수준) |
| 사업자 | 사업자등록증 확인 |
| 보험 | 배상책임보험 증권 확인 |
| 실적 | 완료 확인된 거래 n건 이상 |

**표현에 주의한다.** "Fitter가 보증합니다"가 아니라 "사업자등록을 확인했습니다"다. 보증은 우리가 질 수 없는 책임이고, 그렇게 표시하는 순간 [[서비스 정의|통신판매중개자]] 지위가 흔들린다.

### 4. 표준 계약서 템플릿

**없으면 벌어지는 일.** 도배 중 벽면 곰팡이가 발견돼 추가 작업이 생긴다. 시공자는 "추가 비용 80만원", 고객은 "그건 원래 견적에 포함된 줄 알았다". **구두 합의라 입증할 게 없다.** 양쪽 다 억울하고 플랫폼은 중재할 근거가 없다.

| | |
|---|---|
| 효과 | 중~높음 |
| 구현 난이도 | 중 (PDF 생성은 쉽고, 전자서명은 별개) |
| 법적 요건 | 전자서명은 법적으로 유효하나 입증력은 인증 수준에 따라 다르다 |
| 도입 시점 | 4순위 |

**1단계는 템플릿 PDF 다운로드만.** 서명 없이도 "무엇을 합의했는지"를 문서로 남기는 것만으로 분쟁의 상당 부분이 줄어든다. 범위, 자재 등급, 기간, 금액, 추가 비용 발생 조건, 하자 보수 기간을 항목으로 강제한다.

전자서명은 2단계다. 서명 기능 자체보다 **분쟁 시 입증력**이 중요한데 그건 인증 수준(공동인증서 등)에 달렸고 비용이 붙는다.

### 5. 하자 보수 기간 명시

**없으면 벌어지는 일.** 시공 3개월 뒤 벽지가 들뜬다. 고객이 연락하면 시공자는 "그건 습도 문제"라고 하거나 아예 받지 않는다. **기간과 범위가 합의된 적이 없어서 누가 맞는지 판정할 수 없다.**

| | |
|---|---|
| 효과 | 중 |
| 구현 난이도 | **낮음** (계약서 항목 + 프로필 표시) |
| 법적 요건 | 없음 (당사자 간 약정) |
| 도입 시점 | 계약서와 함께 |

독립 장치가 아니라 **계약서의 필수 항목이자 시공자 프로필의 표시 항목**으로 둔다. "하자 보수 6개월"을 내건 시공자가 경쟁 우위를 갖게 만들면, 강제하지 않아도 시장이 올린다.

### 6. 분쟁 조정 프로세스

**없으면 벌어지는 일.** 분쟁이 생기면 고객은 플랫폼에 온다. 창구가 없으면 리뷰란과 SNS에 쓴다. **플랫폼이 개입하지 않는다는 사실 자체가 평판 문제가 된다.**

| | |
|---|---|
| 효과 | 중 |
| 구현 난이도 | 낮음(접수) / **매우 높음(실제 조정)** |
| 법적 요건 | **개입할수록 중개자 면책이 약해진다** |
| 도입 시점 | 5순위. 신중하게 |

여기에 이 문서에서 가장 미묘한 트레이드오프가 있다.

**신뢰 장치를 제공할수록 "중개자가 아니라 당사자"로 보일 위험이 커진다.** 적극적으로 조정하고 판정하고 배상을 주선하면 고객은 플랫폼을 믿게 되지만, 동시에 플랫폼이 거래에 관여했다는 근거가 쌓인다. 사고가 났을 때 "우리는 중개자일 뿐"이라는 항변이 약해진다.

그래서 초기 형태는 **조정이 아니라 기록과 연결**이다. 분쟁을 접수해 양쪽 주장과 증빙을 기록하고, 소비자원 등 외부 절차를 안내한다. 판정하지 않는다. 실제 조정은 법인화와 전담 인력이 있을 때 검토한다.

### 7. 안전결제 · 에스크로

**없으면 벌어지는 일.** 시공자가 선금 40%를 받고 잠적한다. 고객은 계좌 이체 기록만 있고, 형사 고소는 시간과 비용이 크며 회수 가능성은 낮다. **이게 직거래 구조의 가장 큰 단일 리스크다.**

| | |
|---|---|
| 효과 | **매우 높음** |
| 구현 난이도 | 높음 |
| 법적 요건 | **결제대금예치업 등록 또는 에스크로 제공 PG사 제휴. 개인이 못 한다** |
| 도입 시점 | 법인화 이후 |

**그래서 지금 구현하지 않는다. 못 하는 것이지 안 하는 것이 아니다.**

전자금융거래법상 대금을 예치했다 지급하는 행위는 등록 대상이다. 직접 등록은 자본금·물적요건 때문에 개인 프로젝트로 불가능하고, 현실적 경로는 **에스크로를 제공하는 PG사와 제휴**하는 것이다. 그것도 사업자등록과 심사가 필요하다.

**대신 지금 할 수 있는 것이 있다.** 계약서 템플릿에 **대금 분할 지급 구조를 권고 항목으로 넣는다.** 선금 비율을 낮추고 완료 후 잔금 비중을 높이는 관행을 문서로 유도하면, 에스크로 없이도 잠적 리스크를 줄인다. 강제가 아니라 기본값 제안이다.

## 플랫폼 이탈 — 네 방법 중 무엇이 최고 ROI인가

프롬프트의 핵심 질문이다. 거래를 안에 묶는 방법은 넷이다.

| 방법 | 붙잡는 것 | 비용 | 실제 효과 | 판단 |
|---|---|---|---|---|
| 인앱 채팅 | 소통 | 중 | **낮음** | ❌ |
| 안전결제 | 대금 | **불가** | 매우 높음 | ⏸ 법인화 후 |
| 표준 계약서 | 문서 | 중 | 중 | ○ |
| 리뷰 | 평판 | 낮 | 높음 | ✅ |

**채팅이 가장 오해받기 쉬운 선택이다.** 소통을 붙잡으면 거래가 남을 것 같지만, 한국에서 시공 일정 조율은 결국 전화와 카톡으로 간다. 특히 [[타겟 - 시공자]]는 40~50대에 현장에서 폰으로 일하는 사람들이라 익숙한 도구를 쓴다. **연락처를 주고받는 순간 채팅은 죽는다.** 그리고 연락처 공개는 이 서비스의 설계 자체다. 중간 난이도의 기능을 만들어 낮은 효과를 얻는 조합이라 우선순위가 가장 낮다.

**리뷰가 가장 싸고 효과가 크다.** 이유는 **시공자에게 돌아올 유인이 있기 때문**이다. 평판은 다음 일감으로 이어지므로 시공자가 자발적으로 플랫폼에 남는다. 대금이나 소통과 달리 **평판은 플랫폼 밖으로 가져갈 수 없다.**

**다만 리뷰는 완료 확인 없이는 성립하지 않는다.** 그래서 실제 1순위는 완료 확인이고, 리뷰는 그 위에 얹힌다. 두 개가 한 묶음이다.

**결론: 완료 확인 + 리뷰가 최고 ROI다.** 채팅은 만들지 않는다. 계약서는 분쟁 감소 효과로 정당화되지 지 이탈 방지로 정당화되지 않는다.

## Decision Outcome — 도입 순서

| 순서 | 장치 | 조건 |
|---|---|---|
| 0 | 관리자 승인 + 신고 | **MVP에 이미 있다** |
| 1 | **완료 확인 루프** | 컨택 `ACCEPTED`가 유의미하게 쌓이면 |
| 2 | **리뷰** (완료 확인된 거래만, 사진 필수) | 1이 동작한 뒤 |
| 3 | 인증 등급 (사업자·보험·실적) | 시공자 수가 서류 검수를 감당할 만큼 |
| 4 | 표준 계약서 템플릿 (PDF, 서명 없음) | 분쟁 접수가 실제로 발생하면 |
| 5 | 분쟁 **기록·안내** (조정 아님) | 4와 함께 |
| 6 | 전자서명 | 계약서 사용률이 나오면 |
| 7 | 에스크로 | **법인화 + PG 제휴 이후** |

1과 2가 한 묶음이고 나머지는 상황을 보고 붙인다. **순서의 원칙은 "가장 싼 것이 가장 많은 걸 푸는가"다.**

### 스키마에 미리 열어둘 것

[[ADR-010 - 가격 정책 모델]]과 마찬가지로, **지금 안 만들어도 데이터가 새지 않게** 자리만 봐둔다.

```sql
-- 완료 확인 (1순위). contact_requests 에 얹는다
ALTER TABLE contact_requests
  ADD COLUMN completed_confirmed_by_customer_at TIMESTAMPTZ NULL,
  ADD COLUMN completed_confirmed_by_pro_at      TIMESTAMPTZ NULL,
  ADD COLUMN final_amount                       INT NULL;  -- 실거래가. ADR-010 D단계 데이터원
```

`final_amount`가 중요하다. [[ADR-010 - 가격 정책 모델]]이 제안가(`proposed_amount`)를 1차 데이터원으로 잡았는데, **완료 확인 시점의 최종 금액이 진짜 실거래가**다. 협상으로 깎인 뒤의 값이라 제안가보다 정확하다.

리뷰 테이블은 2순위 시점에 신설한다. 지금 만들면 빈 테이블이 남을 뿐이다. **다만 리뷰의 작성 자격이 `contact_requests`의 완료 확인에 걸린다는 것만은 지금 정해둔다.** 나중에 "어떤 거래에 리뷰를 달 수 있는가"를 다시 설계하면 소급이 안 된다.

---

## Consequences

**긍정**
- 가장 싼 장치(완료 확인)가 리뷰 자격·실거래가·이탈 지표 셋을 동시에 푼다.
- 채팅을 만들지 않기로 명확히 정했다. 중간 비용에 낮은 효과인 기능을 피했다.
- 에스크로를 "안 한다"가 아니라 "못 한다"로 정확히 규정했고, 대신 계약서의 분할 지급 권고라는 대안을 남겼다.
- 중개자 지위와 신뢰 장치의 트레이드오프를 명시했다. 개입할수록 면책이 약해진다는 걸 알고 설계한다.

**부정 / 감수하는 것**
- **완료 확인은 조작 가능하다.** 양쪽이 짜면 거짓 거래를 만들 수 있고, 그러면 리뷰와 가격 통계가 오염된다. 에스크로 없이는 이게 상한이다.
- 리뷰가 없는 초기에는 신뢰 근거가 승인 뱃지와 포트폴리오뿐이다. [[리스크 - 콜드스타트]]와 겹친다.
- 에스크로를 안 하므로 **선금 잠적 리스크가 그대로 남는다.** 이 서비스의 가장 큰 단일 리스크가 미해결로 남는다는 뜻이다. 정직하게 인정한다.
- 인증 등급은 서류를 사람이 검수해야 해서 시공자가 늘면 운영 부담이 선형으로 증가한다.

## 면접에서

"직거래인데 사고 나면 어떻게 하나요"는 반드시 나온다. 답은 이것이다.

**"가장 강력한 장치는 에스크로인데 전자금융거래법상 등록이 필요해서 개인 프로젝트로는 못 합니다. 그래서 못 하는 걸 하는 척하지 않고, 할 수 있는 것 중 ROI가 가장 높은 걸 골랐습니다. 완료 확인 루프입니다. 알림 하나와 양방 확인 플래그면 되는데, 이게 리뷰 작성 자격과 실거래가 데이터와 이탈률 지표를 동시에 줍니다. 그리고 신뢰 장치를 늘릴수록 중개자 면책이 약해지는 트레이드오프가 있어서, 분쟁은 조정하지 않고 기록과 안내까지만 하도록 설계했습니다."**
