# 배포에서 막힌 것들

> 절차는 [[배포 실행 절차]]에 있다. **여기는 그 절차를 따라가는 동안 실제로 걸린 것들**이다.
> 2026-07-26~27 첫 배포에서 겪은 것만 적는다. 예상되는 문제는 안 적는다.

## 한 문장으로

**전부 로컬에서는 재현되지 않는 것들이었다.**

`pnpm build` · `pnpm test` 203개 · `pnpm qc` 0 error 가 전부 통과한 상태에서 배포를
시작했는데, 배포는 여섯 번 실패했다. 실패 원인 중 **로컬에서 미리 잡을 수 있었던 것은
하나도 없었다.** 전부 "내 PC에는 있는데 저기엔 없는 것" 아니면 "로컬 도구가 관대해서
안 드러난 것"이었다.

이게 이번 단계의 유일한 교훈이다. 화면 QC 를 3층으로 나눴을 때와 같은 종류의 발견이다
([[화면 QC 목록]]) — **검사가 통과했다는 말은 그 검사가 보는 범위 안에서 통과했다는 뜻뿐이다.**

## 1. `.gitignore` 가 소스 코드를 삼키고 있었다

가장 오래 걸렸고 가장 무서웠다.

```
.gitignore:28:storage/   →   apps/api/src/infra/storage/s3-storage.adapter.ts
```

`storage/` 라고 쓰면 **이름이 storage 인 디렉터리가 트리 어디에 있든** 걸린다. 로컬
업로드 폴더를 막으려던 규칙이 소스 디렉터리를 같이 잡아서, S3 어댑터와 모듈이
**한 번도 커밋된 적이 없었다.**

왜 안 드러났나 — 파일이 로컬에는 있으니 빌드도 테스트도 QC 도 전부 통과한다. GitHub 을
눈으로 봐도 "폴더가 없다"는 걸 알아채기 어렵다. Railway 가 클론해서 빌드할 때
`Cannot find module` 로 처음 드러났다.

**고친 법**: 앞에 슬래시를 붙여 레포 루트에 고정. `uploads`·`tmp`·`secrets` 도 같은
함정을 안고 있어서 같이 고쳤다.

**다시 안 겪으려면**: 파일시스템과 `git ls-files` 를 대조하면 한 줄로 잡힌다.

```bash
comm -23 <(find apps/*/src packages/*/src -name "*.ts" | sort) <(git ls-files -- apps packages | sort)
```

## 2. Railway 는 pnpm 모노레포를 알아서 못 한다

레포를 연결하면 Railway 가 `apps/web` 과 `apps/api` **둘 다** 서비스로 만들려 든다.
그리고 빌드 명령을 `pnpm --filter @fitter/api build` 로 잡는데, 이건 **반드시 실패한다.**

- `packages/shared`·`packages/domain` 을 안 지어서 `dist/` 가 없다
- `prisma generate` 가 없어서 `PrismaService` 의 타입이 없다

**고친 법**: `railway.json` 을 레포 루트에 두고 명령을 직접 적었다.
`--filter "@fitter/api..."` 의 **점 셋**이 "그 패키지와 그것이 의존하는 것들"이라
`shared → domain → api` 를 위상 순서로 고르고 웹은 빼놓는다.

**Root Directory 를 비워야 한다.** `apps/api` 로 잡으면 `railway.json` 을 그 안에서
찾아서 못 찾고, 자동 감지로 되돌아간다.

## 3. `prisma generate` 순서는 로컬에서 절대 안 걸린다

로컬에는 클라이언트가 **이미 생성돼 있다.** 그래서 빌드 명령에서 `prisma generate` 를
빠뜨려도 통과한다. 빈 컨테이너에서만 터진다.

> [!note] 로컬에서 이 순서를 확인하려고 했더니 다른 게 걸렸다
> `prisma generate` 가 `EPERM ... query_engine-windows.dll.node` 로 실패했다.
> 3001 번에 떠 있던 개발 서버가 그 DLL 을 잡고 있어서였다. **리눅스에서는 안 나는
> 문제**라 배포와 무관하지만, 로컬에서 재현 시도를 할 때 헷갈린다.

## 4. 검증이 없는 환경변수는 조용히 통과한다

환경변수 템플릿을 **플레이스홀더째로 붙여넣었다.**

```
JWT_SECRET="여기에_생성한_값"
STORAGE_ACCESS_KEY_ID="여기에_R2_액세스키"
```

부팅이 실패했는데 **에러는 `JWT_SECRET` 하나만 나왔다.** `env.ts` 에서 그것만
`min(32)` 이고 나머지는 `min(1)` 이라 한글 플레이스홀더도 통과했기 때문이다.

**이게 위험한 이유**: `JWT_SECRET` 만 고치면 서버는 정상으로 뜬다. 그리고
**사진을 올릴 때가 되어서야** `NoSuchBucket` 으로 실패한다. 부팅 검증을 통과했다는 게
값이 맞다는 뜻이 아니다.

같은 이유로 **버킷 이름 단수/복수 불일치**(`fitter-image` vs `fitter-images`)도 부팅
때 안 걸린다.

## 5. R2 는 CORS 가 없으면 업로드가 막힌다 — MinIO 는 다 열어준다

사진은 브라우저에서 R2 로 **직접** 올라간다([[이미지 파이프라인]]).

```js
// apps/web/src/components/ImageUploader.tsx
fetch(uploadUrl, { method: 'PUT', body: file, headers: { 'Content-Type': file.type } })
```

브라우저가 다른 도메인으로 `PUT` 을 보내면서 커스텀 헤더를 붙이므로 **preflight** 가
발생한다. 버킷에 CORS 정책이 없으면 브라우저가 차단한다.

**로컬 MinIO 는 기본이 관대해서 여태 한 번도 안 드러났다.** 개발 스토리지와 운영
스토리지가 같은 S3 API 를 쓴다고 해서 같게 동작하는 게 아니다.

```json
[{ "AllowedOrigins": ["https://<웹 주소>"], "AllowedMethods": ["PUT"],
   "AllowedHeaders": ["content-type"], "MaxAgeSeconds": 3600 }]
```

읽기(`GET`)는 필요 없다. `<img>` 로 불러오는 건 CORS 대상이 아니다.

## 6. Vercel 은 기본으로 `www` 를 본체로 잡는다

루트 도메인을 추가하면 Vercel 이 **`루트 → www` 308 리다이렉트**를 기본으로 건다.

그런데 `WEB_ORIGIN` 은 www 없는 주소로 넣어뒀다. CORS 는 **문자열 정확 일치**를
요구하므로 www 가 붙는 순간 **브라우저의 모든 API 요청이 막힌다** — 화면은 그려지는데
버튼이 하나도 안 먹는, 이미 로컬에서 한 번 겪었던 그 증상이다.

**고친 법**: 루트를 `Connect to an environment → Production` 으로 바꾸고 www 는 지웠다.

## 7. Cloudflare 주황색 구름은 인증서 발급을 막는다

Vercel 과 Railway 는 **각자 자기 인증서를 발급**받는다. 검증 요청이 원본까지 도달해야
하는데 프록시(주황색)면 Cloudflare 가 중간에서 받아버린다. Vercel 은 `Proxy Detected`
라고 경고하고, Railway 는 그냥 대기 상태로 남는다.

| 레코드 | 프록시 |
| --- | --- |
| 루트 CNAME (Vercel) | **꺼야 한다** |
| `api` CNAME (Railway) | **꺼야 한다** |
| `img` (R2) | **켜야 한다** — Cloudflare 가 직접 서빙한다 |
| `_railway-verify.api` TXT | TXT 는 프록시 대상이 아니다 |

**Railway 는 레코드가 두 개다.** CNAME 만 넣고 TXT 를 빠뜨리면 소유권 확인이 안 끝난다.

## 8. DNS 네거티브 캐시 30분 — 여기서 오진했다

레코드가 없을 때 조회하면 **"없음"이 캐시된다.** 이 존의 SOA 기본 TTL 이 1800초라
30분간 유지된다.

레코드를 만들기 전에 `1.1.1.1`·`8.8.8.8`·`9.9.9.9` 를 전부 찔러봤더니, 레코드를 만든
뒤에도 **네 곳 모두 계속 "없음"이라고 답했다.** 권위 서버까지 확인하고 "레코드가 실제로
없다, 지우고 다시 만들어라"고 판단했는데 **틀린 진단이었다.** 사용자 브라우저에서는
그때 이미 정상 접속되고 있었다.

**교훈 둘**:
- 배포 중에는 **레코드를 만들기 전에 조회하지 마라.** 캐시를 스스로 오염시킨다
- 루트 도메인은 **CNAME 타입으로 조회하면 안 나온다.** Cloudflare 가 apex CNAME 을
  평탄화해서 A 레코드로 돌려주기 때문이다. `-type=A` 로 물어야 한다

## 9. Vercel 의 "Add a custom domain" 은 도메인 판매 검색창이다

이미 가진 도메인을 넣었더니 **`.uk.com` 과 `.uk.net` 을 각 $39.99 에 팔려고 했다.**
전혀 다른 도메인이다. 가진 도메인을 붙이는 곳은 왼쪽 사이드바의 `Domains` 다.

같은 화면에 `Vercel DNS` 탭으로 **네임서버를 Vercel 로 옮기라는 안내**도 있는데,
그걸 따르면 DNS 관리가 Cloudflare 를 떠나서 **이미 잘 되던 R2 이미지 도메인이 죽는다.**

## 10. `STORAGE_ENDPOINT` 에는 버킷 이름이 붙어 나온다

버킷 Settings 화면의 `S3 API` 값 끝에 `/버킷이름` 이 붙어 있다. 그대로 넣으면 경로가
두 번 붙는다. **R2 첫 화면의 `Account Details` → `S3 API` 값은 깨끗하다.** 그쪽을 쓴다.

## 11. `PORT` 를 직접 넣으면 안 된다

Railway 가 주입한다. 직접 넣으면 Railway 가 여는 포트와 앱이 듣는 포트가 갈려서
**헬스체크가 영원히 실패한다.** `env.ts` 의 `PORT` 기본값 3001 은 Railway 가 아무것도
안 줄 때만 쓰인다.

## 다음 배포 때 순서를 이렇게 바꾼다

이번에 겪은 순서 문제를 반영한 것이다.

1. **스토리지(R2)를 제일 먼저.** `STORAGE_*` 넷이 없으면 API 가 부팅 자체를 못 한다.
   버킷·공개 도메인·CORS·토큰까지 한 번에 끝낸다
2. **DNS 레코드를 먼저 만들고 그다음에 조회한다.** 반대로 하면 30분을 잃는다
3. **환경변수는 Raw Editor 로 한 번에.** 하나씩 넣으면 플레이스홀더가 남는다
4. 배포 → 헬스체크 초록 → **시드**(`db:seed` · `db:seed:admin`)
5. 검증 3종 — 로그인 후 새로고침 · 사진 업로드 · `/robots.txt`

## 아직 안 한 것

**rate limit.** [[배포 준비 상태]] 참고. 코드가 한 줄도 없고, 신고는 비로그인도 낼 수
있으며 인정되면 대상이 즉시 비공개가 된다.
