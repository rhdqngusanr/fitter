# 기술 스택 결정

> **상태: 확정 (2026-07-25).** 결정 근거 전문은 `brain/50-결정/ADR-001 - 기술 스택 선정.md`.
> 아래 후보·평가축은 결정에 이르기까지의 검토 기록으로 남긴다.

## 결정 (2026-07-25)

**B — Next.js + NestJS + PostgreSQL + S3호환 스토리지** 로 확정했다. 방향은 스타트업·스케일업(제품 엔지니어링), 언어는 풀 TypeScript.

핵심 이유: 이 볼트의 7개 [[구조적 원칙]]과 두 하이라이트([[이미지 파이프라인]] · [[상태머신 - 컨택]])를 NestJS가 거의 1:1로 담는다 — Guard=역할 권한, Interceptor=연락처 노출 통제, event-emitter=도메인 이벤트, DI=어댑터, 순수 TS=도메인 분리. 그리고 Postgres+S3호환+Docker로 벤더 락인이 가장 낮아 "안 갈아엎는다"는 요구에 가장 정직하다. 구체 구성·결과·마이그레이션 경로는 ADR-001 전문 참조.

## 사용자의 요구

"무한한 확장이 가능한 미래를 생각하는 기술 스택."

## 우선순위

1. **확장성.** 포트폴리오지만 실제 사업으로 이어질 수 있다. 트래픽이 100배, 기능이 10배가 되어도 갈아엎지 않는 구조.
2. **혼자 개발한다.** 초기 속도도 중요하다.
3. **국내 취업 포트폴리오로서의 설득력.**
4. **이미지가 핵심이다.** 업로드·변환·CDN 전달이 매끄러워야 한다. → [[이미지 파이프라인]]
5. **비용.** 초기 월 5만원 이하.

## 후보

**A. Next.js(App Router) + Supabase + Vercel**
풀스택 한 방. 인증·DB·스토리지가 붙어 있어 [[이미지 파이프라인]]을 가장 빨리 굴릴 수 있다. RLS로 [[권한 모델]]을 DB 레벨에서 강제할 수 있는 게 특징. 벤더 락인이 단점.

**B. Next.js + NestJS + PostgreSQL + S3**
프론트/백엔드 분리형. API 설계와 아키텍처를 제대로 보여주기 좋다. 중간 난이도.

**C. React + Spring Boot + JPA + PostgreSQL + S3 + AWS**
국내 취업 정석 스택. 백엔드 설계 역량을 보여주기 좋지만 구현량이 가장 많다.

## 평가 축

초기 구현 속도. 확장 한계가 어디서 오는가(어떤 규모, 어떤 기능에서 막히는가). 이미지 파이프라인 구현 난이도. 권한 강제 지점. 검색·필터가 무거워질 때의 경로. 2차 가격 엔진 같은 계산 도메인을 붙이기 좋은가. 벤더 락인과 탈출 비용. 월 예상 비용(초기 / 사용자 1만 명). 국내 채용 시장에서의 신호.

## 중요한 전제

**"무한 확장"은 스택이 주는 게 아니라 경계 설계가 준다.** 어떤 스택을 고르든 지켜야 할 원칙은 [[구조적 원칙]]에 따로 정리했다. 스택 선택보다 그쪽이 실질적으로 더 중요하다.

## 이 결정이 막고 있는 것

Phase 2 이후 전부. 다만 [[P0 - 디자인 시안]]과 [[P1 - 기획]]은 스택과 무관하게 진행할 수 있으므로 지금 당장의 병목은 아니다.
