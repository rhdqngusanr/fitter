# 구조적 원칙

> [[기술 스택 결정]]이 무엇으로 나든 **이건 지킨다.**
> "무한 확장"은 스택이 주는 게 아니라 경계 설계가 준다.

## 1. 도메인을 프레임워크에서 분리한다

비즈니스 로직은 Next.js도 NestJS도 Spring도 모르는 순수한 코드여야 한다. 컨택 상태 전이, 견적 계산, 권한 판정 같은 것들이 프레임워크 타입에 의존하지 않게 한다.

이게 되면 스택을 바꿔도 도메인은 살아남는다. 안 되면 스택을 바꾸는 순간 전부 다시 짠다.

**검증 방법:** 도메인 레이어의 import 문에 프레임워크 이름이 하나도 없어야 한다. [[P5 - 배포와 문서화]]의 P5-5에서 확인한다.

## 2. 외부 의존은 어댑터 뒤에 둔다

스토리지, 이메일, 결제, 알림. 전부 인터페이스를 먼저 정의하고 구현을 뒤에 둔다.

이메일 발송은 MVP에서 콘솔 출력으로 구현하되 인터페이스는 진짜로 만든다. 나중에 SES든 SendGrid든 갈아 끼우면 된다. 스토리지도 마찬가지다.

## 3. 계산의 자리를 미리 비워둔다

[[확장 규약]] 5조. `EstimatePolicy` 인터페이스와 `NoopEstimatePolicy`를 지금 만든다. 2차에 [[리스크 - 가격 신뢰]]를 풀 때 구현체만 갈아 끼운다.

빈 인터페이스를 미리 만드는 게 과해 보일 수 있지만, 이건 코드가 아니라 **의도의 선언**이다. 나중에 코드를 읽는 사람(6개월 뒤의 나 포함)에게 "여기가 확장 지점이다"를 알려준다.

## 4. 상태 변화는 이벤트를 낳는다

[[상태머신 - 컨택]]의 전이는 도메인 이벤트를 발행하고, 알림 같은 부수 효과는 그 이벤트를 구독한다. 상태머신이 알림을 직접 호출하지 않는다.

지금은 이벤트 버스가 인메모리여도 된다. 중요한 건 결합을 끊어두는 것이다. 나중에 메시지 큐로 바꿀 때 발행 지점을 안 고쳐도 된다.

## 5. 목록은 처음부터 커서 페이지네이션

오프셋 페이지네이션은 데이터가 늘면 반드시 느려지고, 무한 스크롤에서 중복·누락을 만든다. 나중에 바꾸려면 API 계약이 깨진다. 처음부터 커서로 간다.

## 6. 읽기 경로에 원본을 태우지 않는다

[[이미지 파이프라인]]의 원칙. 목록에서 원본 이미지를 로드하지 않는다. 이 규칙 하나가 목록 성능의 대부분이다.

## 7. 한 곳에서만 강제한다

권한이든 검증이든 한 레이어에서만 한다. 여러 곳에 흩뿌리면 어디가 진짜 방어선인지 아무도 모르게 되고, 그게 보안 사고의 표준 경로다. → [[권한 모델]]
